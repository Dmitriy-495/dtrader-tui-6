## ГЛАВНОЕ ПРЕДУПРЕЖДЕНИЕ: методология TVP_SNIPER частично утеряна

В `analyzer/config.yaml` и в нескольких `.go`-файлах (`trend.go`,
`macd.go`, `pressure.go`) есть **множественные ссылки** на документ
`TVP_SNIPER.md`, который описывает:
- Роли таймфреймов: 24m = "Главнокомандующий" (EMA+Angle+RSI), 8m =
  "Генерал" (EMA+MACD), 1m = быстрый ориентир (только EMA).
- Пороговые правила, например "26%-74% — запрет торговли" (упомянуто
  в комментарии `trend.go` про RSI-диапазон, но точный смысл и полный
  список подобных правил — только в самом документе).
- "Диапазоны тестирования" для периодов индикаторов — текущие
  значения в `config.yaml` (EMA 9/21 на 1m, 12/24 на 8m, 50/72 на
  24m) помечены как "стартовые... НЕ окончательные боевые цифры".

**Этого файла физически нет ни в одном архиве, который у меня был.**
Я (предыдущий Клод) искал его во всём доступном коде — не нашёл.
Это значит одно из двух:
1. Файл существует у автора локально/в другом месте и просто не
   попал в переданные мне архивы — **спроси прямо в первом же
   сообщении**, прежде чем писать код сигналов "по интуиции".
2. Методология существует только в голове автора и частично
   закодирована в упомянутых параметрах/комментариях — тогда твоя
   первая задача не писать код, а **вытащить эту методологию из
   автора через явные вопросы**, зафиксировать её письменно (в
   идеале — воссоздать сам TVP_SNIPER.md), и только потом кодить.

Не изобретай торговые правила сам, даже правдоподобные — это чужие
деньги на реальной бирже (баланс аккаунта на проде реальный, ~25
USDT на момент этой сессии, но не в этом суть — принцип тот же при
любой сумме).

## Согласованная граница ответственности (уже решено, не нужно заново обсуждать)

Это явно закодировано в комментариях `analyzer/internal/indicator/
pressure.go`:

> Порог для решения (напр. >1.5 для LONG) — уже зона signal-engine,
> не analyzer, см. согласованную границу ответственности сервисов.

**analyzer** — считает сырые T/V/P, ничего не решает, порогов не
знает. **signal-engine** (новый сервис, тебе предстоит его построить)
— читает `indicators:*` из Redis, применяет торговые правила,
принимает решения. Значит вероятная архитектура:

```
dtrader-6/signal-engine/   ← новый сервис, по аналогии с analyzer/
  cmd/main.go
  internal/config/          читает symbols/thresholds из signal-engine.yaml
  internal/reader/          читает indicators:* из Redis (тот же паттерн, что analyzer/internal/reader)
  internal/rules/           чистая математика: T/V/P → сигнал (LONG/SHORT/HOLD), без Redis-протокола
  internal/publisher/       пишет signals:{symbol} обратно в Redis
```

Не факт, что это точная структура — сверься с автором, но общий
принцип (read Redis → чистая логика решений → write Redis) уже
согласован и его стоит уважать, а не выдумывать заново.

## Практические факты, которые тебе понадобятся сразу

**Формат `indicators:*` в Redis** (уже используется в TUI, проверен
на реальных данных прода):
```json
// indicators:trend:{tf}:{symbol} — tf ∈ {1m, 8m, 24m}
{"ema_fast":64336.78,"ema_slow":64316.65,"direction":"neutral","angle":79.54,"rsi":62.97,"macd_histogram":0,"ts":1786998812534}

// indicators:volume:{tf}:{symbol}
{"buy_vol":17718,"sell_vol":0,"delta":17718,"spike":false,"ts":1786998812534}

// indicators:pressure:{symbol}  (БЕЗ {tf} — P один на весь символ)
{"bid_vol":41053,"ask_vol":79193,"imbalance":0.518,"ts":1786998812534}
```

**direction** — строка `"up"/"down"/"neutral"`, с epsilon-порогом
0.05% относительной разницы EMA (см. `trend.go:neutralEpsilon`) —
уже отфильтрован дребезг на флэте, не нужно повторять эту защиту
на твоей стороне.

**Известное ограничение analyzer (см. `pressure.go` комментарий
"НАМЕРЕННО не включаем детекцию поглощения крупных ордеров")**: P
считается на **одном срезе** стакана, не серии во времени — если
твоей сигнальной логике нужна динамика давления (не только текущее
значение, но и его изменение), эта возможность **отложена, не
реализована**, придётся либо добавлять в analyzer, либо считать
самому в signal-engine из истории.

**MACD включён только на 8m** (`macd_fast/slow/signal = 0` на 1m и
24m — явно выключено, ноль означает "не считать", не "период 0").

## Технический процесс — не пропускай, это стоило реальных багов

Раздел 15 CHECKPOINT.md dtrader-6 (полный документ ещё доступен,
если у тебя есть архив с ним) формулирует правило: **"закоммичено"
≠ "задеплоено"**. Один раз это привело к тому, что бот молча висел
на проде без реконнекта несколько дней, пока баг не заметили.
Практическое следствие для тебя: после любого изменения `analyzer`
или нового `signal-engine`, **проверяй на реальном сервере**
(`strings <бинарник> | grep -c <новая_функция>`), что задеплоенный
бинарник реально содержит твой код — не полагайся на "должно быть,
раз закоммичено".

Другой найденный урок этой сессии: **числа, которые кажутся правильными
на бумаге, не всегда правильны на практике**. Несколько раз в этой
сессии (расчёт ширины UI-панелей, EMA-спред шкалы) я делал арифметику
вручную, она выглядела логично, но реальный рендер показывал другое —
пришлось измерять факт, а не полагаться на расчёт. Если будешь
писать бэктестинг/симуляцию сигналов — та же дисциплина: проверяй
на реальных исторических данных, не только на unit-тестах с
придуманными числами.

## С чего начать (предложение, не жёсткий план)

1. **Спроси про TVP_SNIPER.md прямо в первом сообщении.** Это
   блокирует осмысленную работу — без методологии можно написать код,
   но не сигналы, которым можно доверять.
2. Пока ждёшь ответа — можешь начать с каркаса `signal-engine/`
   (config, reader из Redis, пустой rules-пакет с TODO) и написать
   тесты на **чтение** существующих `indicators:*` — это безопасная,
   полезная работа, не зависящая от точных торговых порогов.
3. Как получишь методологию — реализуй `rules/` как чистые функции
   (T/V/P snapshot → Signal), тестируй их изолированно на конкретных,
   реалистичных числах (в этой сессии оказалось критично важно
   тестировать на **реальных** прод-данных, не выдуманных — в TUI
   есть готовые примеры реальных JSON-снапшотов в
   `internal/tui/*_test.go`, можешь взять оттуда для калибровки).
4. **Обязательно спроси, готов ли автор сначала тестировать сигналы
   в режиме "только логировать/показывать", прежде чем разрешать
   реальные ордера** — bot сейчас read-only (не отправляет ордера
   на биржу вообще), и это стоит явно обсудить, прежде чем менять.
